\subsection{Structure of an Autonomous Robot}
An autonomous robot has two main goals: complete its task without human
intervention and perform it efficiently. Efficiency as a metric depends
entirely on what we are designing for --- an autonomous robot that can navigate
a track on its own. For the case of Navilott, this means a robot that can
navigate a street-style course on its own --- following a lane, stopping at
stop signs and obeying traffic lights.

\paragraph{A robot's architecture.}
In robotics, this is often called "autonomous navigation", a part of
"autonomous control," where the robot controls itself to perform a task, such
as following a line or avoiding obstacles~\citep{douglas2020autonav1}. A robot
can have many different methods to measure and sense its environment ---
camera, sonar, ultrasonic, IR, etc. Subprocesses in the robot's software can
use these measurements to form a map of the environment. The robot's estimation
system can use the map to calculate the robot's position and orientation in the
world. The robot's navigation system can then use these estimates to determine
the robot's decision about what to do next. The robot's control system can then
actuate motors in response to these decisions. Actuation is performed in two
layers: the control loop which sends PWM signals, and the driver which switches
battery voltages based on the PWM signals that actuate the motors via current.
Feedback from encoders on the motor can then be routed back into estimation and
navigation systems to ensure that the decision was taken in the right place.

The robot can then be divided into 6 main areas:

\begin{figure}[H]
    \centering
    \input{figures/tikz/robot_loop}
    \caption{The six areas as a closed loop.}
    \label{fig:robot-loop}
\end{figure}

\begin{itemize}
    \item \textbf{Capture}: the robot's sensors and how they capture the environment
    \item \textbf{Perception}: the robot's processing algorithms and how they interpret those measurements
    \item \textbf{Estimation}: the robot's estimation system and how it generalizes those measurements
    \item \textbf{Navigation}: the robot's navigation system and how it forms decisions about the environment based on those perceptions
    \item \textbf{Control}: the robot's control system and how it moves the robot around those decisions
    \item \textbf{Actuation}: the robot's actuation system and how it actually moves the robot
\end{itemize}

\subsection{Single-Board Design}
% Think about: the criteria you judged by (control rate, $100 BOM, 12 V,
%   local processing, dev time); MCU-only vs Pi+MCU vs Pi-only; the PRD
%   recommends a microcontroller, so Pi-only departs from its guidance.
% Evidence: vision_stack/docs/architecture.md ("Decision: Pi Zero 2 W only")
%           MCU option and packet format: docs/archD1/
Our first concern was how the start of the stack would interact with the end of
it --- meaning how we would connect the robot's perception system to the motor
actuation. To achieve this, three options were considered:

\begin{figure}[H]
    \centering
    \input{figures/tikz/board_options}
    \caption{Where each area runs under the three options.}
    \label{fig:board-options}
\end{figure}

\begin{itemize}
    \item \textbf{MCU-only}: An STM32 or Arduino runs the perception pipeline and
          drives the motors directly.
    \item \textbf{Pi-only}: The Pi runs the perception pipeline and drives the
          motors directly via PWM signals to a motor driver.
    \item \textbf{Pi + MCU}: The Pi processes perception and sends a packet over
          UART to an STM32 or Arduino, which executes a fast, real-time PID loop
          and generates the PWM signals.
\end{itemize}

\paragraph{Why not MCU-only?}
The Raspberry Pi was a necessary addition because of our robot's camera-centric
design. Intense computer vision needs a lot of RAM to run efficiently, ISP and
CSI-2 interface to capture video quickly and bypass CPU overhead, and OpenCV
library to perform the intense image processing we would require. For instance,
to process a frame that is $480\times270$ in color pixels would require 389 KB
of RAM --- more than what is found in most microcontrollers.

\paragraph{How a Pi + MCU would affect architecture.}
Integrating an MCU into our design would require a new protocol to transfer the
data between the Pi and the MCU, synchronization of clocks between the two
devices (the Pi captures and stamps frames based on its clock while encoders
from the motors would work on the MCU's clock), and managing two separate
codebases. These different challenges, while making the architecture more true
to a real-world robot, would also make it more difficult to maintain.

\paragraph{Decision: Pi-only.}
As such, a single-board design was chosen (The Raspberry Pi Zero 2 W) --- which
sacrifices speed of a dedicated motor control loop for the simplicity and
testability of the Pi, as well as accepting the overhead from the Linux
scheduler. However, these tradeoffs were considered when developing the stack
and are discussed in Section~\ref{sec:linux_scheduler}.

\paragraph{Camera.}
Originally, we were using a Raspberry Pi Cam V2 module as our camera, which
featured an IMX219 sensor. However, its field of view is cropped by the mode
selection of the Pi. This added a heavy blindspot of 22 cm to the robot's
vision and made it incapable of viewing both the lane lines and the traffic
light in one frame while at a stop line. Details can be found in
Section~\ref{sec:capture}. In response, we opted for another type of camera:
the Innomaker's Cam-MIPI290RAW, a wide-angle camera that is compatible with the
Raspberry Pi's CSI-2 interface. This allowed us to achieve a fuller field of
view and reduced our blindspot down to 10 cm, but at the cost of the lens
producing a distortion effect which would require software to correct
(Section~\ref{sec:capture}).

\paragraph{Battery monitoring.}
Intrinsically, the Pi does not have an analog input and thus does not have a
way to capture any voltage running through it --- it requires some external
component to monitor it --- the batteries feature no Battery Management System
(BMS). That is where the ADS1115 comes into play. As per
Section~\ref{sec:problem}, we are to warn the system after falling beneath
$10.5\,\text{V}$ and stop navigation after the robot falls under
$9.9\,\text{V}$.

\paragraph{IMU.}
Our robot will need a way to measure and verify its angular turns during
intersection logic and lane keeping. The Pi has no internal gyroscope that can
measure its angular velocity, nor its acceleration. The MPU6050 fills this gap,
supplying the Estimation system with additional information about the robot's
yaw. Details can be found in Section~\ref{sec:estimation}.

\paragraph{Actuation.}
The robot will need some way to actually move around the course as well as a
way to accurately control how current is sent to the motors. The Pi's power
pins can only supply a few milliamps for other peripherals connected to it.
However, these pins cannot supply a current large enough to move the motors,
lest the Pi becomes damaged. In this, the TB6612FNG motor driver switches
battery power to the N20 motors via an H-Bridge. Details can be found in
Section~\ref{sec:software_architecture}.

\paragraph{Encoder.}
To measure the robot's speed, we need a way to measure the speed of the wheels.
The Pi has no internal encoder that can measure the speed of the wheels. The
Encoders are used to measure the speed of the wheels. Details can be found in
Section~\ref{sec:estimation}.

\paragraph{Interface.}
Finally, a way to communicate with the user about the robots state, time
limits, and a way to physically start the robot are required
(Section~\ref{sec:problem}). In this, the TM1637 7-segment display and a small
button are used. The display is used to show navigation information and the
time while the robot runs through a course (and to display its final time)
while the button doesn't allow for the motor to actually process software
commands until it is pressed. Details can be found in
Section~\ref{sec:software_architecture}.

\paragraph{Power.}
To power on all of these different peripherals, the robot uses 3S 18650 battery
cells, 12.6 V full, 11.1 V nominal, 9.0 V empty. The buck converter is used to
normalize and distribute 5V power rails --- it is used to power the Pi while
the batteries are directly routed to the motor driver. The Pi powers the
remaining components via its 3.3V pin.

\paragraph{PCB.}
The PRD requires the integration of the main SBC and its hardware components to
be mounted via a printed circuit board (PCB). All of the hardware components
(except the camera) are routed through the PCB, with the chassis serving as
mounting points for motors, the camera, the display, the button, and the
batteries. The PCB uses headers that are soldered to the PCB to connect to each
component --- each component has a place on the board it sits and cables that
route power and data to any of the externally seated components listed earlier.

\subsection{Software Language}
% Think about: Python as glue over OpenCV's C++; the bindings it gave you
%   (OpenCV, GStreamer/libcamera, pigpio); the GIL and interpreter cost,
%   and whether that shows up in P1.
Due to the complexity of the problem, we required a language that had access to
complex computer vision algorithms, data visualization, and iteration speed.
Because of these needs, we chose Python because it featured 3 main solutions to
our problem:

\begin{itemize}
    \item \textbf{GStreamer}: Python's bindings for OpenCV allows it to access
          GStreamer from its backend, which is an open-source multimedia framework.
          It provides access to the camera, and allowed us to interface with the camera
          and process the frame data from it.
    \item \textbf{OpenCV}: Python's bindings for OpenCV, a computer vision
          library, provided access to the complex algorithms that we needed to
          perform our computer vision tasks.
    \item \textbf{Testing}: Python allows us to abstract away the complexities
          of the different algorithms and libraries that we needed to use. Because
          of this, we were able to take advantage of different techniques to test,
          such as duck-typing and mocking, to verify that our system performed as
          expected.
\end{itemize}

\paragraph{GStreamer.}
For interfacing with the camera, Python had access to the GStreamer library, an
open-source multimedia framework written in C. It works on multiple threads,
chaining together elements --- data flows from a source element, through
various filter/transform elements, and finally ends at a sink element.

\paragraph{OpenCV.}
For computer vision, Python has access to the OpenCV library, an open-source
computer vision library written in C++. It contains a wide range of algorithms
for image processing, object recognition, and more.

\paragraph{Global interpreter lock.}
However, accepting Python as our language was not without its tradeoffs. Python
runs in an interpreter, and because its types are only checked at runtime, each
operation costs far more than the equivalent in C. Python also has a Global
Interpreter Lock (GIL), a lock that the interpreter holds while it runs Python
code. It prevents multiple threads of Python bytecode to run in parallel across
different cores --- only a single thread can run Python bytecode at a time, on
whichever core Linux gives it.

\paragraph{Python as an acceptable tradeoff.}
Although Python's cost per operation is higher than C's, Python's overhead is
acceptable because the per-pixel work never runs in Python --- it is handled by
C/C++ code.

\subsection{Background Threads}
The codebase splits up its processes across 5 different kinds of threads:

\begin{itemize}
    \item \textbf{Main Loop}: This is the main thread that runs the main
          loop of the program. It handles the 4-phase pipeline and the
          communication between the main loop and the other threads.
    \item \textbf{SensorHub}: This thread is responsible for reading from
          the IMU and the encoders every 10\,ms, loading into a buffer until
          it's drained. It remains asleep for most of the robot's life.
    \item \textbf{Motor Watchdog}: This thread is responsible for braking
          the motors if it does not receive a command from the main pipeline
          for 0.5 seconds. But if Linux kills the Python process, the watchdog
          dies with it, while pigpio keeps the PWM at its last duty.
    \item \textbf{Pigpio Callbacks}: This thread reads and delivers encoder edges
          to the total encoder counter.
    \item \textbf{GStreamer/libcamera}: GStreamer backend interfaces with the Pi's
          libcamera software to feed the main loop (OpenCV's VideoCapture) with the
          camera's video stream.
\end{itemize}

\paragraph{Pigpio.}
The pigpio daemon is its own process that runs in the background of the Pi. It
is initialized during the system's startup and remains running while it is on.
It timestamps the encoder edges and owns the pins controlling the motors,
keeping their PWM signals online --- even if the main loop stalls.

\paragraph{How the GIL splits work with OpenCV.}
When the program starts, the main loop holds the GIL. Whenever it calls into
OpenCV it releases the lock, and a waiting thread --- the sensor hub, the motor
watchdog or the pigpio callbacks --- can take it. While the main loop runs
Python code instead, a waiting thread must wait: only after 5\,ms does Python
ask the holder to release the lock, unless the thread lets it go.

\paragraph{How the sensor hub works with the GIL.}
For the sensor hub, which reads the IMU every 10\,ms, a wait of up to 5\,ms is
a large share of its period. Two changes shorten how long each reading needs
the lock. Each reading fetches the IMU's 14-byte sample block in a single
I\textsuperscript{2}C transfer and then releases the GIL once it's done. The
I\textsuperscript{2}C bus runs at 400\,kHz so each transfer finishes sooner.
Every reading is also timestamped when it is taken, so a late read is recorded
at its true time and does not become a heading error.

\paragraph{Where does GStreamer fit?}
The GStreamer pipeline runs a C thread and is separate from the GIL, allowing
it to perform its own tasks without interrupting the main loop. However, it
spends a lot of its time waiting for the next frame.

\subsection{Tooling}
% Think about: Make (setup.mk once per Pi, session.mk every boot,
%   vision_stack/Makefile as the command list), pytest, git/PRs, the
%   linkers and debug views, AI-assisted sessions.
% Architecture shaped by tooling: one place for stage order; replayable
%   frame sources; estimation imports no hardware; diagnostics in a
%   separate process.
% Evidence: docs/guides/make.md; git log for when each .mk was added

The tooling of the Pi was actually an afterthought when it came to developing
the software --- how to reproduce the same environment across multiple Pis and
how to manage daily friction. As problems arose, we designed tooling to address
them.

\paragraph{Consistency and reproducibility.}
During the early stages of development, many of the components were wired up on
a breadboard. We had a few issues with power management which caused some
components to pull more current than expected, damaging them --- the Pi being
one of them. Instead of manually reinstalling each dependency, possibly missing
some dependencies in the environment, we decided to use a Makefile script to
install them --- which would exclude the ones that we would not keep in the
final design. This was a direct countermeasure to avoid cluttering the Pi with
failed and dropped packages and to make the Pi more reproducible. This was the
purpose of our first tool, the \texttt{setup.mk} file.

\paragraph{Daily friction.}
However, additional initialization was needed on every boot: the clock on the
Pi always started unsynchronized and was a major source of frustration ---
preventing updates to the system and causing naming conflicts. The school's
network would block the Pi's connection to the NTP server and since the Pi has
no battery-backed clock, it could not keep time while the Pi was powered off.
Furthermore, the Pi utilized a virtual environment to run the robot's Python
code. On every boot, we had to set the clock by hand, activate the environment,
and launch pigpio. To make the process easier, we implemented a script which
did all three. This was our second tool, the \texttt{session.mk} file.

\paragraph{Python virtual environment.}
The virtual environment we used was set up to mitigate OS conflicts between
installed libraries and packages:

\begin{itemize}
    \item Many of our drivers --- Adafruit and TM1637 libraries --- come from pip. We
          often ran into issues in the terminal installing them because the OS would
          refuse their installation to protect its Python environment.
    \item The robot packages could conflict with some of the OS packages.
    \item A broken package could be easily removed and reinstalled.
    \item We also needed to expose the virtual environment to packages installed with
          \texttt{apt} --- such as Picamera2 --- which binds to the system's libcamera.
\end{itemize}

The virtual environment sees the foundation of the camera stack and holds the
robot's own pip packages.

\paragraph{Making an installable package.}
With the virtual environment initialized, the code needed to be set up as an
installable package. A lack of organization across the codebase made it
difficult to run and test after each iterative change. Python projects often
describe themselves in a \texttt{pyproject.toml} file, which describes the
project's metadata and dependencies. After calling \texttt{pip install -e .},
the project is now an installable package --- it installs the package as a link
to the source folder so any changes are reflected and don't need to be
reinstalled. \texttt{setup.mk} runs this command automatically.
